# 設計原則

仕様策定、API・モデル設計、実装、テスト、ドキュメント、運用手順のすべてで KISS、YAGNI、MECE を使い、必要な複雑さだけを扱う。

## KISS（Keep It Simple, Stupid）

要件を満たす最も単純な解を選ぶ。複雑さは必要になってから追加し、過剰な設計を先に持ち込まない。

- まず要件の最小集合だけを満たす。延長戦の要件は後回しにする。
- 依存は最小化し、既存の型、モジュール、標準ライブラリ、プロジェクトの仕組みを優先して再利用する。
- 1つの変更が必要な範囲に閉じるよう、責務と依存を分ける。
- 早すぎる最適化や抽象化を避け、必要になってから導入する。
- 命名、I/O、例外の扱いを一貫させ、暗黙の規約を増やさない。
- データ構造は素直にし、モデルや型で表現できる制約を分岐やコメントだけに任せない。
- ライブラリ選定は必要十分なものにする。

## YAGNI（You Aren't Gonna Need It）

現在の Issue と受け入れ条件に必要なものだけを実装する。

- 将来必要になるかもしれないという理由だけで、抽象化、継承、設定、引数、互換層を追加しない。
- 具体的な利用例のない共通関数、汎用Mixin、拡張ポイントを作らない。
- 今回使わないモデル項目、APIパラメータ、エラー種別を先回りして定義しない。
- 将来要件が発生したときに小さく変更できる余地だけを残し、未使用の仕組みは作らない。

## MECE（Mutually Exclusive, Collectively Exhaustive）

要件、責務、テスト、レビュー観点を整理するときに、重複と漏れを減らす。

- まず対象範囲と分類軸を定め、同じ観点の分類を重ねない。
- 1つの業務ルールや処理責務が複数の層・アプリへ重複しないようにする。
- 受け入れ条件に対して、変更に関係する正常系、境界、失敗、権限、外部依存を確認する。
- 網羅性を理由に、Issue と無関係な将来ケースまで追加しない。対象範囲の外側は明示的に扱わない。
- 同じ責務の処理を別の名前で増やさず、一つの場所へ集約する。

## 避けること

- 想定ユースケースがない抽象化、継承、汎用Mixinの導入
- 小さな変更に対する大規模リファクタリング
- 設定を増やして、コードで済む単純な処理を複雑にすること
- 複雑なマジック、メタプログラミング、隠れた副作用

## 判断基準

- この変更は要件を満たす最短経路か。
- 3か月後の自分や同僚が5分で読めるか。
- 依存、公開インターフェース、影響範囲を小さくできるか。
- 要件、実装、テストの間に重複や漏れがないか。
- 失敗時の挙動が明確で、ロールバックしやすいか。
