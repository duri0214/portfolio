# 編集ルール（スタイルガイド） — AI Agent

適用対象: `docs/qiita/ai_agent.md`

## 目的

- Phase 1では、Qiita記事「（途中）AI Agent を試作する」の原本を内容を変えずにGitHubで管理する。
- Phase 2では、原本を出発点として、刷新後の `ai_agent/` の実装と記事の説明を対応付ける。
- 記事に書かれた設計・機能・処理フローが、対象フェーズの実装状態と分離しないようにする。

## 適用スコープ

- Qiita原本または刷新後のAI Agentの概要
- `ai_agent/` の実装、処理フロー、ツール、ガードレール、履歴管理の説明
- 記事から参照する関連Issue、コード例、検証手順
- 非対象: 記事の記述だけで実装済みと扱うこと、記事のテーマをルールで固定すること

## ルール

1) フェーズごとの扱いを分ける
   - Phase 1では、原本のタイトル、主題、説明順、表現を原則として変更しない。
   - Phase 2では、ターン制会話からSkill Chain型Agentへ、記事のタイトル、主題、構成、用語を変更してよい。

2) 現在の実装と将来計画を分ける
   - 現在の処理は `ai_agent/` の実装を確認してから記述する。
   - ベクトル検索、動的モデレーション、未実装の外部連携は、実装済みと断定しない。
   - 改善途中の内容は、関連IssueまたはPhase 2への参照を付ける。

3) 実装状態と記事の説明を一致させる
   - 記事に書く主要な処理フローは、対象フェーズの実装を確認してから記述する。
   - クラス名、モデル名、Tool名、イベント名、API名は実装と一致させる。
   - 処理を追加・変更した場合は、記事のフロー、コード例、検証手順を同時に確認する。

4) 設計上の責務を実装に合わせる
   - Factory、Repository、Service、Value Object、Agent、Toolなどの責務は、対象フェーズの設計に合わせて説明する。
   - 現在存在しない層や、刷新で廃止した層を実装済みのように説明しない。
   - DDDの一般概念を残す場合も、刷新後のAgent、Tool、実行履歴などの責務に合わせて説明する。

5) リンクと履歴を維持する
   - 記事原本、`ai_agent/` のソース、親Issue、対象PhaseのIssueを参照できる状態にする。
   - #310、#324などの関連Issueは、刷新後も関係がある場合だけ残し、不要になったリンクは更新または削除する。
   - ブランチ固有のURLやローカルパスを記事に残さない。

6) コードブロックの表記を統一する
   - Pythonファイルは `python:ai_agent/domain/service/input_processor.py` のように対象ファイルを付ける。
   - コンソール操作は `bash:console` を使う。
   - 実装を確認していないコードを記事へ新規掲載しない。

7) 実装と記事を同じ変更単位で確認する
   - Phase 1は原本のGitHub化と記事管理ルールの整備を中心とする。
   - Phase 2で実装や設計を大きく変えた場合は、変更後のコードと記事を同じPRまたは相互参照できる変更単位で確認する。

## チェックリスト（レビュー用）

- Phase 1ではQiita原本との差分が最小限になっているか。
- Phase 2では刷新後のAgentの目的・構成・処理を説明しているか。
- 記事の処理フローが対象フェーズの `ai_agent/` と矛盾していないか。
- 実装済み、想定、改善途中、廃止予定の機能が区別されているか。
- Agent、Tool、イベント、永続化の責務が実装と一致しているか。
- 関連Issueとソースコードへのリンクが、現在の設計と関係しているか。
- コードブロックのファイルパスとタグが既存のQiita記事ルールに沿っているか。
- Phase 1で実装変更を混ぜていないか。
