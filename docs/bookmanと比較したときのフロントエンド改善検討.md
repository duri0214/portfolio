# bookman と比較したときのフロントエンド改善検討

## 目的

`bookman` のフロントエンドを見たときに感じる良さが、React / Next.js に起因するものなのか、それとも CSS、情報設計、画面密度、コンポーネント設計に起因するものなのかを整理する。

そのうえで、`portfolio` のフロントエンドを現行構成のまま改善できる範囲と、React / Next.js や HTMX を検討すべき条件を分ける。

## 現時点の仮説

`portfolio` のトップページや各アプリ紹介画面を良くするだけなら、Next.js へ寄せる必要は薄い。

`bookman` のホーム画面にある図書カードの揺れ、紙らしい質感、余白、ボタンの押し心地は、React / Next.js の機能というより、HTML 構造と CSS の表現によって成立している。これらは Django テンプレート、Bootstrap、最小限の独自 CSS で十分に移植できる。

一方で、`bookman` の管理画面のように、一覧、検索条件、作成/編集ダイアログ、フォーム状態、API 通信、チャート、テーブル操作が同じ画面内で絡み合う場合は、React / Next.js の価値が出やすい。

## bookman の良さを分解する

### CSS / デザイン由来の良さ

- 図書カード風のビジュアルが、アプリの主題と直結している。
- `@keyframes` と `transform` による軽い揺れで、静的なトップページに動きがある。
- 紙、罫線、番号、影、奥行きがあり、画面の第一印象が強い。
- CTA ボタンの hover、影、境界線が控えめで、業務アプリらしい落ち着きがある。
- `prefers-reduced-motion` を考慮すれば、アクセシビリティを損なわずに演出できる。

この領域は React / Next.js である必要はない。`portfolio` では Django テンプレートと CSS で十分再現できる。

### React 由来の良さ

- UI 部品をコンポーネントとして分割しやすい。
- 一覧、フォーム、モーダル、確認ダイアログ、通知などを状態と一緒に扱いやすい。
- フォームにフォームが重なるような複雑な画面状態を整理しやすい。
- 入力中の値、検索条件、選択行、編集中データ、API エラーなどをクライアント側で持ちやすい。
- UI 単位のテストを書きやすい。

ただし、`portfolio` の現状では、この強みが必要な画面は多くない。静的な説明ページ、詳細ページ、通常のテーブル表示、シンプルなフォームであれば Django 側で十分対応できる。

### Next.js 由来の良さ

- ファイルベースルーティングで画面を整理しやすい。
- SSR / SSG / ISR など、ページ生成戦略を選べる。
- API Route を使ってフロントエンド側に BFF 的な層を置ける。
- React Server Components など、React アプリとしての構成を深く使える。
- フロントエンドの型、テスト、Lint、ビルドを一体で管理しやすい。

ただし、これらは運用コストも伴う。Node.js、npm、依存パッケージ、ビルド、脆弱性対応、デプロイ構成が増える。`portfolio` のように Django が既にサーバーサイドレンダリングを担っている場合、単純な画面改善のために Next.js を足すのは過剰になりやすい。

## portfolio で現行構成のまま改善できること

- トップページ Hero の再設計。
- 実績カードの見た目、余白、情報量、CTA の整理。
- CSS の `transition`、`transform`、`@keyframes` による軽い演出。
- Bootstrap のグリッド、カード、ボタン、バッジを使った画面密度の改善。
- D3.js などを使ったグラフ表示。
- 通常の HTML テーブルによる情報表示。
- Django テンプレートでのコンポーネント風 partial 分割。

グラフは D3.js や既存の軽量ライブラリで足りる。表は、表として十分に情報を表示できればよい。DataGrid 的なリッチ操作が不要なら React に寄せる必要はない。

## HTMX を検討すべき条件

HTMX は、JavaScript アプリを作りたいときではなく、サーバーが返す HTML 断片で画面の一部を差し替えたいときに向く。

検討に値する例:

- 検索条件を変えたら一覧だけ更新したい。
- ページ全体をリロードせずにページネーションしたい。
- モーダル内フォームを送信し、成功時に一覧だけ差し替えたい。
- バリデーションエラーをフォーム部分だけに返したい。
- Django の view / template / form を活かしたまま、少しだけ非同期にしたい。

不要な例:

- カードを揺らす。
- hover 演出を付ける。
- Hero をかっこよくする。
- 表示だけのカード一覧を整える。

これらは CSS で足りる。

## Next.js と HTMX の比較

| 観点 | Next.js | HTMX |
| --- | --- | --- |
| 主な目的 | React ベースのフロントエンドアプリ構築 | サーバー HTML の部分更新 |
| 状態管理 | クライアント側で複雑な状態を扱いやすい | 状態は基本的にサーバー側に寄せる |
| Django との相性 | API 境界を設ける必要がある | Django view / template / form と相性が良い |
| ビルド | Node.js とフロントビルドが必要 | 基本的に不要 |
| 依存 | npm パッケージが増える | 依存は小さい |
| UI の自由度 | 高い | サーバー HTML 中心なので中程度 |
| 複雑な CRUD | 得意 | 軽中量なら対応可能、複雑化するとつらい |
| 単純な演出 | 可能だが過剰 | 不要。CSS でよい |
| サプライチェーンリスク | npm 依存が増えやすい | 相対的に小さい |
| portfolio への適性 | 現時点では低め | 動的な部分更新が必要になれば候補 |
| bookman への適性 | 複雑な管理 UI が主なら妥当 | 業務フローが単純なら置き換え候補 |

## 判断基準

### CSS でよい

- 動きが見た目の演出に閉じている。
- サーバー状態と関係しない。
- hover、focus、揺れ、フェード、影、奥行きだけで足りる。

### Django テンプレートでよい

- 表示データはサーバーで決まる。
- 画面遷移やフォーム送信は通常のリクエスト/レスポンスで十分。
- テーブルやカードの表示が主目的。
- 状態をブラウザ側に長く保持する必要がない。

### HTMX を検討する

- 画面全体ではなく一部だけ更新したい。
- Django の form / validation / template を保ちたい。
- SPA にするほどではないが、毎回フルリロードは重い。

### React / Next.js を検討する

- 画面内の状態が多く、サーバー往復だけでは操作感が悪い。
- 一覧、検索、編集、選択、モーダル、チャート、通知が密に連動する。
- フォームが多段で、入力途中の状態管理が重要。
- クライアント UI のテストや型安全性を厚くしたい。
- フロントエンドを Django とは別のアプリとして育てる理由がある。

## portfolio の当面方針

`portfolio` は、Django + Bootstrap + 独自 CSS のまま改善する。

最初に取り組むなら、`home` トップページの Hero と実績カードの情報設計を見直す。`bookman` の図書カード演出のように、各アプリの主題を象徴する軽いビジュアルを CSS で作る方向がよい。

HTMX は、検索、絞り込み、ページネーション、フォーム部分更新など、明確な非同期要件が出た時点で検討する。

Next.js は、`portfolio` には現時点では不要。導入するなら、単なるデザイン改善ではなく、React / Next.js が必要な画面状態や運用上の理由がある場合に限定する。

## bookman の再評価ポイント

`bookman` については、Next.js が必要かどうかを見た目ではなく管理 UI の複雑さで判断する。

確認する観点:

- CRUD 画面でクライアント状態がどれだけ必要か。
- 作成/編集/削除/検索/選択/通知が同一画面でどれだけ絡むか。
- MUI DataGrid、チャート、ダイアログが本当に必要か。
- Django テンプレート + HTMX に寄せた場合、コード量と操作感が改善するか悪化するか。
- npm 依存、ビルド、脆弱性対応、デプロイの運用コストに見合う価値があるか。

現時点では、`bookman` のホーム画面の良さは Next.js の強みではない。管理画面の複雑さが Next.js 継続の主な判断材料になる。
